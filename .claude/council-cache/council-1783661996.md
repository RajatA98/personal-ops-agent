## 🔳 Codex - gpt-5.5
**Overall Assessment**

The PRD is directionally strong and internally consistent with the chosen ambitious v1. It captures the right safety posture: propose, review, approve, never silently act. The biggest gaps are not “scope is too large”; they are missing operational boundaries, data semantics, permission/error behavior, and acceptance criteria that Presearch will need to choose the right architecture.

I would not lock this PRD unchanged. I would lock it after tightening the items below.

**Critical / Lock-Blocking Issues**

1. **No explicit trust boundary between local app, model, integrations, and memory**

The PRD says local-first “where practical” and model-swappable, but does not define what data may leave the device, what must stay local, or what context is sent to the reasoning model.

Why it matters: this directly affects model choice, storage design, privacy posture, and whether voice/memory/calendar/email data can be sent to cloud APIs.

Add requirements like:

```md
The app must classify data into:
- Local-only: raw HealthKit data, OAuth tokens, iMessage text payloads unless user opts in.
- Model-eligible: summarized calendar context, approved memory snippets, user-entered prompts.
- Never-sent: credentials, full OAuth tokens, unredacted message/email bodies unless explicitly approved for a task.

Every model call must be logged with: timestamp, purpose, input categories, model provider, and whether raw external content was included.
```

2. **Memory correction model is underspecified**

The PRD correctly says memory supports correction and expiration, but it does not define whether corrections mutate entities, append revisions, supersede prior facts, or preserve provenance.

Why it matters: this app’s trust depends on memory being auditable. “What did I decide?” and “mark this as wrong” require a real versioning model.

Add:

```md
Memory entities must be append-only at the audit layer.
Corrections create a new revision that supersedes prior values while preserving source, timestamp, and reason.
Queries must prefer active non-expired revisions and expose uncertainty when conflicting memories exist.
```

3. **Proposal approval semantics need to be stricter**

The PRD says no proposal auto-approves, which is good. But it does not define what “approve” means for different action classes.

Approving “remember this”, “schedule this”, “modify goal plan”, and “create calendar event” are very different.

Add an action taxonomy:

```md
Proposal actions are typed:
- remember_fact
- create_agent_calendar_event
- update_agent_calendar_event
- modify_goal_plan
- mark_goal_progress
- snooze_open_loop
- dismiss_signal

Each type has an explicit execution handler and required confirmation copy.
Approving one Proposal may execute only the action described in that Proposal, not inferred follow-up actions.
```

4. **OAuth/token storage and revocation are not requirements yet**

Gmail and Google Calendar integrations require OAuth. The PRD mentions minimum scopes, but not token handling, account disconnect, refresh failure, or revocation.

Why it matters: Presearch cannot choose secure persistence and auth architecture without this.

Add:

```md
OAuth tokens must be stored in iOS Keychain.
The app must support disconnecting each integration.
Revoked/expired credentials must degrade gracefully and create an Ops Inbox item or settings alert, not silently fail.
The app must never log access tokens, refresh tokens, or authorization headers.
```

**Major Issues**

5. **No offline/degraded-mode behavior**

The app depends on Google APIs, model calls, voice, HealthKit, and Shortcuts. The PRD should define what happens when any dependency is unavailable.

Examples to specify:

- Morning briefing when Gmail sync fails.
- Voice interaction when model API is unavailable.
- Calendar write retry behavior.
- HealthKit permission denied.
- Shortcut payload malformed or delayed.
- Model response timeout.

Suggested requirement:

```md
The app must show source freshness for major briefing inputs:
calendar last synced at X, Gmail last scanned at Y, HealthKit last read at Z.
If a source is unavailable, the briefing must say so rather than implying completeness.
```

6. **Calendar conflict rules are too vague**

“Conflict detection” is required, but not defined.

Clarify:

- Does conflict mean literal time overlap only?
- Are travel buffers considered?
- Are tentative/all-day events conflicts?
- Are agent-owned events allowed to conflict with real calendar events?
- Can goal tasks be soft-flexible versus hard-fixed?
- What happens across time zones?

Add event metadata:

```md
GoalTask schedule blocks must have:
- flexibility: fixed | movable | optional
- priority
- earliest/latest acceptable time
- expected duration
- conflict policy: block | warn | allow
```

7. **Generalized goal engine needs minimum domain boundaries**

The PRD says generalized schema with playbooks, not hardcoded to Training/Job Search. That is good, but it does not define what a playbook contains.

Add:

```md
A goal playbook defines:
- intake questions
- milestone schema
- task generation rules
- progress signals
- review cadence
- slip detection rules
- schedule block templates
- completion criteria
```

Without this, the implementation may become either too generic to be useful or secretly hardcoded.

8. **Voice interface lacks privacy and interruption requirements**

“Full conversational turn-taking” is broad. The PRD should define minimum behavior.

Add:

- Push-to-talk or wake mode?
- Is audio retained?
- Are transcripts stored as memory by default?
- Can the user interrupt TTS?
- Can the agent ask clarification questions?
- What happens if transcription confidence is low?

Example:

```md
Voice transcripts are not stored as memory unless they produce an approved or confirmed memory update.
The user can interrupt playback.
Low-confidence transcriptions require confirmation before creating proposals or memory.
```

9. **Gmail classification needs false-positive/false-negative handling**

The PRD says Gmail surfaces commitments/events as Proposals. It should define dedupe, threading, and rescans.

Add:

```md
Email-derived Proposals must include the source message/thread ID.
The system must deduplicate repeated scans of the same thread.
If a user marks a proposal as wrong, similar future extraction should be downranked or suppressed for that source pattern.
```

10. **iMessage via Shortcuts has important product constraints**

The PRD correctly avoids passive/background reading. But the Shortcuts path should be more explicit.

Risks:

- User must manually configure automation.
- iOS may require confirmation depending on automation type/settings.
- Payload content may be partial.
- Sender identity mapping may be limited.
- Attachments/media are likely out of scope.

Add:

```md
iMessage ingestion is best-effort and user-configured.
The app must treat Shortcut-provided messages as untrusted external text with explicit source metadata.
The app does not guarantee complete message coverage.
Attachments, reactions, edits, and deleted messages are out of scope for v1 unless explicitly captured by Shortcut payload.
```

11. **HealthKit use needs consent and interpretation limits**

The PRD says sleep/recovery signals inform pacing. It should avoid overclaiming medical or training advice.

Add:

```md
HealthKit signals may adjust pacing recommendations but must not provide medical advice.
The app must display when a pacing suggestion was influenced by sleep/recovery data.
The user can disable HealthKit influence without disabling goals.
```

12. **No explicit acceptance criteria for core flows**

Before Presearch, each core flow should have testable success criteria.

For example:

```md
Morning Briefing acceptance criteria:
- Shows today’s real calendar events and agent-owned events separately.
- Shows active goal commitments due today.
- Identifies at least one slipped item when yesterday’s planned task lacks completion evidence.
- Displays source freshness.
- Can be generated without Gmail/HealthKit if permissions are absent.
```

Do this for Morning Briefing, Evening Capture, Goal Planning, Ops Inbox, Voice, Weekly Review, and Conflict Detection.

**Minor / Clarifying Issues**

13. **“iPhone 17 Pro” may be too specific as a platform target**

Fine if intentional, but Presearch should still define minimum iOS version and hardware capabilities. Device model alone is not enough for API decisions.

14. **“Claude Fable as build tool” is absent from the PRD**

The note mentions Fable, but the PRD itself only says model-swappable and post-Fable cost changes. If Fable affects implementation constraints, add it as a build-process constraint, not runtime architecture.

15. **No data export/delete detail**

The PRD says export/delete supported. It should specify whether export includes memory revisions, proposals, logs, source references, and local-only data.

16. **No background execution expectations**

iOS background limits matter for calendar/Gmail polling, HealthKit reads, and Shortcut ingestion. The PRD should state whether sync is foreground-only, background best-effort, or notification-driven.

17. **No notification policy**

Morning/evening prompts, Ops Inbox alerts, weekly review, and slipped goals imply notifications. Add frequency, quiet hours, and user controls.

18. **No observability/debug surface**

For a single-user agent, a lightweight “why did it say that?” surface is important.

Add:

```md
Agent outputs must expose supporting sources where practical: calendar event IDs, proposal IDs, memory entity IDs, or source summaries.
```

**Recommended PRD Additions Before Lock**

I would add five sections before moving to Presearch:

1. **Data Boundaries & Privacy Classes**
Define local-only, model-eligible, external-source, and audit-log data.

2. **Proposal Execution Semantics**
Define proposal action types, approval behavior, expiration, idempotency, and source traceability.

3. **Memory Lifecycle**
Define create, correct, supersede, expire, query, and conflict handling.

4. **Integration Failure Modes**
Define degraded behavior for Calendar, Gmail, Shortcuts, HealthKit, voice, and model provider failures.

5. **Acceptance Criteria**
Add testable criteria for each core flow.

**Verdict**

The PRD is good enough to preserve the ambitious product direction, but not yet precise enough to lock for technical selection. The main risk is that Presearch will otherwise choose technologies against vague promises instead of concrete requirements around privacy, memory correctness, proposal execution, sync, and degraded operation.

I’d revise the PRD with the above requirements, then move to Presearch.

## Synthesis

**Consensus**: Single-provider run (codex only configured) — no cross-provider consensus/divergence to report.

**Assessment of the response**: This is a different kind of critique than the earlier Problem Summary review. That one pushed back on *scope size* (which the user correctly overruled — build capability, not platform policy, was the limiting factor). This one pushes back on *specification precision* — it doesn't ask to cut anything, it asks to define behavior the PRD currently leaves implicit: what data can leave the device, how memory corrections are versioned, what "approve" means per action type, how OAuth tokens are stored/revoked, what happens when a dependency is down, what "conflict" means precisely, what a goal playbook contains, voice privacy/interruption rules, email dedup, iMessage coverage limits, HealthKit consent boundaries, and testable acceptance criteria per flow. These are legitimate gaps regardless of how ambitious v1 is — an ambitious PRD still needs precise semantics, or Presearch ends up choosing architecture against vague promises.

**Recommendation**: Fold in the 5 recommended additions (Data Boundaries & Privacy Classes, Proposal Execution Semantics, Memory Lifecycle, Integration Failure Modes, Acceptance Criteria per flow) before locking. None of this walks back the ambitious scope decision — it makes the ambitious scope buildable with confidence.
