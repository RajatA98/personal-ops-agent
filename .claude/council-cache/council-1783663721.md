## 🔳 Codex - gpt-5.5
**Overall Assessment**

The sequencing is directionally sound: foundation → Google integrations → daily loop → proposal safety layer → LLM → voice → Mac sync. The biggest issue is that the plan claims each phase is independently demoable, but Phases 3, 4, and 7 are too broad to be reliable single implementation units, and several acceptance criteria are too vague for another AI coding tool to turn into good tickets without inventing details.

I would hand this off only after tightening phase boundaries and adding a cross-cutting “Phase 0 / Engineering Foundation” section.

**1. Sequencing And Dependencies**

Mostly sound, with three dependency concerns.

Phase 1 should include CloudKit-readiness even if CloudKit is not enabled until Phase 7. SwiftData + CloudKit has model constraints that can bite later: optional/default values, relationship shape, uniqueness, migration behavior, stable IDs, deletion semantics. If Phase 7 “turns on sync” after six phases of local-only modeling, it may force schema rework. Add to Phase 1:

- SwiftData models designed and validated for future CloudKit compatibility.
- Stable app-level IDs separate from SwiftData object identity.
- Explicit migration/versioning strategy.
- A small test target proving model containers can initialize cleanly with the intended schema.

Phase 3 currently says goal planning produces a schedule proposal that writes to the agent-owned calendar after approval, but the full Proposal state machine is not until Phase 4. That creates a dependency mismatch. Either:

- Move a minimal `create_agent_calendar_event` proposal/approval path into Phase 3, then expand Proposal types in Phase 4; or
- Keep Phase 3 schedule proposals as non-executable previews only, with no calendar write until Phase 4.

Phase 4 says “verify no code path lets an LLM-suggested action bypass the Proposal queue,” but the LLM is introduced in Phase 5. Reword Phase 4 around non-LLM proposal sources, then Phase 5 should add the explicit LLM bypass tests.

**2. Phases That Should Be Split**

Phase 3 is too large. It includes goal schema, two playbooks, planning, calendar-backed scheduling, Morning Briefing, Evening Capture, Weekly Review, and HealthKit. That is the core app plus another external integration. Split it:

- **3A — Goal Engine + Playbooks**: schema, Training/Job Search playbooks, task generation, progress model, slip detection using seed/local data.
- **3B — Daily Loop UI**: Morning Briefing, Evening Capture, Weekly Review from deterministic context.
- **3C — HealthKit Pacing**: permission flow, reads, freshness, disable switch, labeled pacing suggestions.

Phase 4 is also too large. It combines safety-critical Proposal execution, Gmail extraction/dedupe, conflict detection, and Shortcuts/iMessage ingestion. Split it:

- **4A — Proposal System + Ops Inbox**: state machine, execution handlers, approval/dismiss/snooze, audit logs.
- **4B — Signal Sources**: Gmail-derived proposals, dedupe, mark-as-wrong downranking.
- **4C — Conflict Detection + Shortcuts Intake**: goal conflict rules and untrusted text ingestion.

Phase 7 should be split. “Mac Companion App & CloudKit Sync” is two major risks:

- **7A — CloudKit Sync Hardening**: enable sync, conflict behavior, migrations, dedupe, tombstones, multi-device test matrix.
- **7B — macOS Target**: shared code, platform-specific permissions, Mac UI, voice behavior, Google auth strategy.

Phase 6 may also need two internal milestones: STT/TTS plumbing first, then conversational turn-taking and voice-first Evening Capture.

**3. Acceptance Criteria Quality**

Several criteria are good but not ticket-ready. The biggest problem is references like “matches the PRD’s per-flow acceptance criteria” in Phase 3 and Phase 6. That creates weak tickets because the implementer has to chase another artifact and decide what counts as done.

Make each phase self-contained. Examples:

For Phase 1, add concrete tests:

- Unit test: correcting a memory creates revision `n+1`, keeps revision `n`, marks `n` superseded, and default query returns only `n+1`.
- Unit test: expired memory is excluded from default query and included in history query.
- Unit test: two active conflicting memories return an uncertainty/conflict result, not an arbitrary winner.

For Phase 2, add measurable auth/API criteria:

- Token refresh is tested with an expired access token.
- Revoked refresh token creates reconnect state.
- Calendar write retry uses the same caller-provided event ID and results in one event.
- Gmail sync stores message ID, thread ID, received date, and scan timestamp without storing unnecessary raw body content unless explicitly needed.

For Phase 3, replace the PRD reference with explicit checks:

- Morning Briefing generated from fixture data shows real calendar events, agent-owned events, due goal tasks, slipped items, and source freshness.
- Evening Capture updates `DailyLog`, `GoalProgress`, and `OpenLoop` from a text/tap flow.
- Weekly Review summarizes completed, slipped, and next-week tasks for each active goal.
- Goal plan approval creates only agent-owned calendar events, or explicitly does not write until Phase 4 depending on the chosen boundary.

For Phase 4, acceptance criteria need negative tests:

- Each Proposal type has a test proving approval invokes only its handler.
- Dismissed/snoozed/expired proposals do not execute.
- Duplicate Gmail scan for same thread/message does not create another pending Proposal.
- Malformed Shortcut payload is dropped or surfaced as an error, not guessed into memory.
- Conflict detection has fixtures for fixed/fixed, fixed/movable, movable/optional, and `block/warn/allow`.

For Phase 5, “coherent and grounded” is too subjective. Add eval-style fixtures:

- Given deterministic briefing context, model output must reference only provided facts.
- Given absent memory, Q&A returns “I don’t know” with no fabricated source.
- Tool registry test proves no write-capable external-calendar/email tool is exposed.
- Model-call logging test verifies required metadata is persisted and tokens/headers are never logged.

For Phase 6, “feels good” is valid as a risk note, not an acceptance criterion. Add measurable checks:

- Playback can be interrupted within a defined latency target.
- Low-confidence transcript path requires confirmation before creating Proposal/memory.
- Transcript is not persisted unless confirmed/approved.
- ElevenLabs failure falls back to `AVSpeechSynthesizer`.

For Phase 7, “reasonable sync window” must be defined. For example:

- Sync convergence target: within X minutes under normal connectivity.
- Test matrix: iPhone creates/approves Proposal, Mac observes; Mac resolves, iPhone observes; offline edit then reconnect; duplicate prevention; deletion/tombstone behavior.
- CloudKit migration test with existing local data.

**4. Missing Week-One Engineering Concerns**

Add a Phase 0 before Phase 1. A real team or AI coding tool will otherwise lose time deciding basic structure.

Recommended **Phase 0 — App Scaffold, Tooling, And Engineering Contracts**:

- Xcode project/workspace structure, bundle IDs, iOS/macOS deployment targets, signing assumptions for free Apple ID sideloading.
- Test targets: unit tests, UI tests, integration-test fixtures, mock services.
- Dependency policy: native URLSession vs package clients, secret handling, no token logging.
- App architecture: module boundaries such as `Data`, `Integrations`, `Goals`, `Proposals`, `Reasoning`, `Voice`, `UI`.
- Error model: typed app errors, user-visible degraded states, retry policy, source freshness conventions.
- Logging/observability: local logs, privacy redaction, model-call audit schema.
- Configuration: debug/staging/prod-ish local configs, Google OAuth client config, Gemini/ElevenLabs key storage.
- CI/local validation: `xcodebuild test`, lint/format if used, basic simulator test command.
- Fixture strategy: fake Google API, fake HealthKit data, fake reasoning provider, fake clock.
- Data export/delete requirement from the PRD.
- Notification policy: morning/evening prompts, weekly review, Ops Inbox alerts, quiet hours.
- Background execution policy: what syncs in foreground only, background-best-effort, or via user-triggered refresh.

**Concrete Plan Edits I’d Make**

1. Insert Phase 0 for scaffold/tooling/testing/error conventions.
2. Add CloudKit-compatible schema constraints to Phase 1 even if sync waits.
3. Split Phase 3 into Goal Engine, Daily Loop, and HealthKit.
4. Move minimal Proposal approval into Phase 3 or defer calendar writes until Phase 4.
5. Split Phase 4 into Proposal Core, Gmail Signals, and Conflict/Shortcuts.
6. Make Phase 5’s LLM safety tests explicit and fixture-based.
7. Split Phase 7 into CloudKit sync hardening and Mac app target.
8. Replace “matches PRD criteria” with copied, phase-local, testable acceptance criteria.

The plan is strategically good, but it is currently more of a milestone narrative than an implementation-ready breakdown. The main fix is to make each phase smaller, self-contained, and testable without relying on downstream systems or implicit PRD interpretation.

## Synthesis

**Consensus**: Single-provider run (codex only) — no cross-provider divergence to report.

**Assessment**: This is high-value, concrete feedback, not scope pushback. It catches two real sequencing bugs (Phase 3 references calendar writes that depend on Phase 4's Proposal system; Phase 4 references an "LLM bypass test" for a system not introduced until Phase 5), flags three phases (3, 4, 7) as too broad to be reliable single implementation units, and — most importantly for a plan about to be handed to another AI tool for ticketing — replaces vague "matches the PRD's criteria" references with concrete, fixture-based, testable acceptance criteria per phase. The recommended Phase 0 (scaffold/tooling/error conventions/fixture strategy) is also a real gap: without it, an implementer has to invent foundational structure ad hoc in the middle of Phase 1.

**Recommendation**: Adopt all 8 concrete edits. This will expand the plan from 7 to roughly 13 phases — more granular than the original 3-7 guideline, but justified: the goal here is a plan precise enough to hand to another tool for ticket generation without that tool having to guess at missing details or discover the sequencing bugs mid-build.
