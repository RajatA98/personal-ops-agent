## Phase 1 — Local Data Model & Versioned Memory System ✅ (merged from `2533ff1`)

- **Schema**: ten `@Model` entities — revisionable MemoryEntities (`DailyLog`, `Commitment`, `Goal`, `GoalProgress`, `Decision`, `Preference`, `OpenLoop`, `Pattern`, `Proposal`) plus structural child `GoalTask` (child of `Goal`; corrections to it happen via `modify_goal_plan` Proposals, not revisions).
- **Identity model**: `appID` (stable per-revision app-level ID), `factKey` (semantic identity shared across a fact's revisions/conflicting claims), `supersededByAppID` (audit back-pointer).
- **Revision mechanism**: all writes via `MemoryStore` (`insert`/`correct`/`expire`/`resolve`/`history`). `correct()` copies value fields to a new row (revision n+1), stamps the old row superseded — never mutates in place. `resolve(factKey:)` returns `.none`/`.resolved`/`.conflict` — conflicts are explicit, never an arbitrary winner. Expiry evaluated against injected `Clock`.
- **CloudKit-shaped**: no unique attributes (appID uniqueness is a write-time convention), all attributes optional-or-defaulted, all relationships optional with explicit inverses, enums stored as raw String. `DataSchemaV1: VersionedSchema` + `MemoryMigrationPlan` (baseline); `DataModule.schemaVersion = 1`. CloudKit sync itself OFF until Phase 7A (host-side compat proven; `.automatic` container needs an iCloud-entitled device build).
- **Latitude decision**: shared vocabulary (`TaskFlexibility`, `ConflictPolicy`, `ProposalType`, `ProposalStatus`, new `MemorySource`) relocated to `Core/Vocabulary.swift` — Data must store these types and can't import Goals/Proposals. Relocation, not redefinition.
- **Verified**: `swift test` 47/47 (33 + 14 new); `xcodebuild test` TEST SUCCEEDED; zero warnings; strict-concurrency-clean.
- **Gotchas for later phases**: module named `Data` collides with `Foundation.Data` (can't module-qualify `Data.X`); `Pattern` collides with a C Quickdraw type in test targets (infer, don't name in type position); generic `#Predicate` over the MemoryEntity protocol doesn't compile — store filters post-fetch; `MemoryStore` is not Sendable (construct on the ModelContext's owning actor); always set `factKey` on insert (two entities left at default `""` read as one fact).

## Phase 2 — Google Calendar & Gmail Integration ✅ (implemented; live-capable, mock-verified)

Live-credential caveat: real Google OAuth requires the user to create their own Google Cloud OAuth client. The code is fully live-capable; behavior is verified against URLProtocol-mocked integration tests + fixtures until the user supplies `Secrets/Config.local`. Manual live steps: **`docs/GOOGLE_SETUP.md`** (step-by-step, non-technical).

- **Scope choice** (justified in `GoogleOAuthConfig` + `docs/GOOGLE_SETUP.md`): `calendar.readonly` (read real calendars, never write) + `calendar.app.created` (create + write **only** app-created calendars — makes real-calendar writes *structurally* impossible, the strongest form of Safety Rule #2) + `gmail.readonly` (list/search + snippet for Phase 4B classification). Deliberately rejected the broader `calendar.events` (write-all) and any `gmail.send`/`gmail.modify`.
- **OAuth**: native PKCE flow, no client secret. `PKCE` (CryptoKit S256), `AuthorizationRequest` (pure URL builder + callback/state parsing), `GoogleOAuthService` (code exchange + silent refresh; `invalid_grant` → `IntegrationError.tokenRevoked`), `AuthorizationCodeProvider` protocol with `WebAuthorizationCodeProvider` (ASWebAuthenticationSession, reversed-client-ID callback scheme), `GoogleAuthenticator` (actor; connect/disconnect/`validAccessToken` with silent refresh + reconnect-on-revoke). Redirect URI = reversed client ID (`com.googleusercontent.apps.<id>:/oauth2redirect`).
- **Tokens**: `TokenStore` protocol; `KeychainTokenStore` (Security framework, `afterFirstUnlock`, upsert) for prod; `InMemoryTokenStore` (Fixtures) for `swift test`. `OAuthToken` redacts its secret material in `description`/`debugDescription` (Safety Rule #5).
- **Clients**: `GoogleCalendarRESTClient` (actor) — listCalendars, `ensureAgentCalendar` (find-or-create "Personal Ops Agent" calendar, cached), listEvents, idempotent `createEvent` (caller key → deterministic base32hex Google event ID via `GoogleEventID`; 409 duplicate → GET existing → exactly one event), update/delete, all writes guarded to the agent calendar only. `GmailRESTClient` (actor) — `gmail.readonly` list + `format=metadata` fetch; stores only messageID/threadID/receivedDate/scanTimestamp/snippet via `GmailMetadataStore` (in-memory now; **Phase 4B swaps in a durable SwiftData-backed store** for cross-launch dedupe).
- **Degradation**: `IntegrationStatusStore` (`@MainActor @Observable`) is the single source of truth for per-source connection/freshness/degraded state; `IntegrationStatusReporting` (async, Sendable) lets the actor clients/authenticator report in. Phase 4A reads this to surface reconnect prompts as Ops Inbox items (the Inbox doesn't exist yet; Settings is the reconnect home now).
- **Transport**: `HTTPTransport` protocol (`URLSessionTransport` prod), `HTTPErrorMapper` (status → typed `AppError` per source), `withRetry` (uses `RetryPolicy` + `AppError.isRetryable` — the sanctioned retry path). Tests inject a `URLSession` backed by `MockURLProtocol`.
- **UI**: `IntegrationsSettingsView` (per-integration status, freshness text, degraded/reconnect notice, Connect/Disconnect); `RootView` is now a `TabView` (Memory | Integrations). `IntegrationsEnvironment` (`@MainActor`) is the composition root: `.live(clientID:)` or `.unconfigured()` (missing `Config.local` → app still runs, Connect surfaces a clear config error, no crash). App entry registers `Config` secrets with `RedactingLogger` at startup.

## Phase 3A — Goal Engine & Playbooks ✅ (implemented; TDD, mock-verified)

Deterministic, LLM-free goal engine + two real playbooks, all in `Sources/Goals/` (module was previously an empty skeleton). No calendar writes anywhere in the phase — structurally guaranteed (the `Goals` target does not depend on `Integrations`).

- **Playbook schema is data, not code** (`Playbook.swift`): `GoalPlaybook` is a pure value type carrying exactly the PRD's eight elements as data — `intakeQuestions` / `milestoneTemplates` / `taskRules` / `progressSignals` / `reviewCadence` / `slipRule` / `scheduleBlockTemplates` / `completionCriteria`. Component value types: `IntakeQuestion`(+`IntakeAnswer`/`IntakeAnswers`), `MilestoneTemplate`, `TaskRule`, `ProgressSignal`, `ReviewCadence`, `SlipRule`, `ScheduleBlockTemplate`, `CompletionCriterion`. **The two goal types differ only by these data values** — there is no per-playbook branch anywhere in the engine. This is the PRD's explicit red-flag guard ("shared real mechanics, not two hardcoded paths behind a wrapper"), enforced by `PlaybookDistinctnessTests` which drive the *same* `generatePlan(...)` call for both goals and assert structural differences (flexibility mix: training has `fixed`/`block` anchors, job search has zero; disjoint metric sets; different milestone keys; different completion criteria).
- **Two shipped playbooks** (`Playbooks.swift`, `PlaybookLibrary`): `triathlonTraining` (key `"training"`) — dawn-pool swims + Saturday long ride/brick are `fixed`/`.block` immovable anchors, run/strength softer; base→build→peak→taper→race milestones; tracks swim/bike/run km. `jobSearch` (key `"job_search"`) — 5 applications/wk + interview prep are `movable`/`.warn`, networking/portfolio `optional`/`.allow`, **nothing `fixed`/`.block`** (a job search yields to real meetings); resume→pipeline→interviewing→offers→decision funnel; tracks applications/interviews/offers. Look up by `PlaybookLibrary.playbook(forKey:)`.
- **Planner** (`GoalPlanner.swift`): one algorithm plans every goal type. Reads `taskRules` and expands each across the weeks between `now` and `targetDate` (horizon clamped to ≥1 week so a plan is never empty). Produces pure value types `GeneratedPlan`/`PlannedTask`/`PlannedMilestone` (no SwiftData dep → testable with no container). **Scheduling is pure `TimeInterval` arithmetic off the week start** (no `Calendar`/timezone) so plans are byte-for-byte deterministic in tests. `flexWindow(flexibility)` sets each task's `latestAcceptable`: `fixed`→0 slack, `movable`→6h, `optional`→3d — this is what makes flexibility drive different slip deadlines.
- **Schedule PREVIEW** (`SchedulePreview.swift`): `SchedulePreview` + `ProposedBlock` are pure inspect-only value types describing what agent-calendar events *would* look like. `SchedulePreviewBuilder.preview(for:window:)` (default window = first 7 days) filters plan tasks into blocks. **Zero calendar I/O by construction.**
- **Slip detection** (`SlipDetector.swift`): `slippedTasks(tasks:progress:rule:asOf:)` over persisted `GoalTask`+`GoalProgress`. A task slips iff not `isComplete`, `asOf > latestAcceptable + slipRule.gracePeriod`, and (if `requiresCompletionEvidence`) no `GoalProgress` falls in its window. Open-ended tasks (nil `latestAcceptable`) never slip.
- **Persistence** (`GoalPlanMaterializer.swift`): bridges `GeneratedPlan` → persisted `Goal`(revision 1, `factKey` = `goal:<slug>`) + `GoalTask` children via `MemoryStore` (constructed on the context's actor). Follows the Phase 1 pattern (`goal.tasks = [...]; store.insert(goal)`). No calendar writes.
- **UI** (`GoalsView.swift`): new **Goals tab** in `RootView` (Memory | Goals | Integrations). List of active goals → `GoalDetailView` (milestones, tracked metrics, 7-day schedule preview labeled "inspect only, not written to calendar"). `CreateGoalView` = playbook picker + dynamic intake form → `GoalPlanner` → `GoalPlanMaterializer.persist` into the live `modelContext`. Functional, not polished (per phase scope).
- **Fixture change**: `FakeGoogleCalendarAPI` gained a `writeCallCount` (increments on every create/update/delete, even idempotent-deduped creates) so `SchedulePreviewTests` can assert the engine performs **zero** calendar writes and that the counter genuinely moves on a real write (proving the zero is meaningful). Existing `createdEvents` semantics unchanged.
- **Package changes**: `UI` target now depends on `Goals`. New `.testTarget("GoalsTests", dependencies: ["Goals","Core","Data","Fixtures","Integrations"])` (Integrations only so the zero-writes test can drive the calendar fake).
- **Verified**: `swift test` **104/104** (80 prior + 24 new); package builds warning-free, strict-concurrency-clean. `xcodebuild test` (iPhone 16 Pro, iOS 18.2) **TEST SUCCEEDED** (app launches with the 3-tab shell). All three Phase 3A acceptance criteria have dedicated tests: distinct-plans-from-shared-schema (`PlaybookDistinctnessTests`), slip flag on no-evidence fixture (`SlipDetectorTests`), preview-writes-nothing via zero `writeCallCount` (`SchedulePreviewTests`).
- **Handoff — 3B (daily loop UI)**: consume `SlipDetector.slippedTasks(...)` to surface slipping items in the Morning Briefing (inject the same `FakeClock`); read `Goal.tasks` (filter `isComplete`/window for "due today"); `GoalProgress.metricKey`s come from the playbook's `progressSignals`; Evening Capture writes `GoalProgress` via `MemoryStore` and can flip `GoalTask.isComplete`. The Goals tab already renders a preview you can lift patterns from. Keep it deterministic (Swift-assembled), no LLM.
- **Handoff — 3C (HealthKit pacing)**: pacing feeds into the same plan generation — cleanest injection point is adjusting `TaskRule.weeklyFrequency`/`expectedDuration` or annotating `PlannedTask` before materializing. `GoalPlaybook` is a value type; a HealthKit-adjusted variant is a data transform, not new engine code. Label HealthKit-influenced output at the `PlannedTask`/preview layer.
- **Handoff — 4A (proposal execution)**: `ProposedBlock` maps 1:1 to a `create_agent_calendar_event` Proposal payload (title/start/end + agent calendar). A goal-plan preview → batch of `create_agent_calendar_event` Proposals is the approval path; use `GoalTask.appID` as the idempotency-key seed. `modify_goal_plan` corrects `GoalTask`s (they're structural children, corrected via Proposal, not memory revisions — per Phase 1). `GoalPlanMaterializer` is the write path a `modify_goal_plan` handler can reuse.
- **Handoff — 4C (conflict detection)**: every `GoalTask` carries `flexibility`/`priority`/`earliestAcceptable`/`latestAcceptable`/`expectedDuration`/`conflictPolicy`, all populated by the planner from playbook data. Training yields `fixed`/`.block` pairs, job search `movable`/`optional` with `.warn`/`.allow` — good cross-goal fixture material (a training block vs a job-search block is exactly the PRD's conflict example). `PlannedTask` mirrors the same fields pre-persistence if you want to detect conflicts on a preview before materializing.
- **Gotchas**: (1) `Goals` deliberately does **not** depend on `Integrations` — keep it that way; that's what makes "no calendar writes" a structural guarantee, not a convention. (2) The planner's week math is raw `TimeInterval` (epoch = Thursday), not `Calendar` — a `weekday: 7` template lands 6 days + startHour past the week start; don't assume calendar-aware weekday alignment. (3) `MemoryStore` is not Sendable — `GoalPlanMaterializer` takes it by value and must be constructed on the context's actor (the UI does this on `@MainActor`). (4) Plans over an 8-week horizon are ~60–80 tasks; fine at single-user scale but preview to a window, don't render all of them.

## Phase 3B — Daily Loop UI: Briefing, Capture, Weekly Review ✅ (implemented; TDD, mock-verified)

Deterministic, LLM-free daily loop: Morning Briefing assembly, Evening Capture writes, Weekly Review rollup, one-tap complete/skip, and a Home/Lock-Screen widget. New SPM target `DailyLoop` holds all the testable assembly logic; three new SwiftUI tabs render it. No new write paths to calendar/Gmail (read-only against them); HealthKit deliberately untouched (owned by the concurrent 3C sibling — the briefing only marks HealthKit *freshness* absent).

- **New module `DailyLoop`** (`Sources/DailyLoop/`, deps `Core`+`Data`+`Integrations`+`Goals`): the deterministic assembly layer, entirely value-type output so **Phase 5 can hand these structures straight to the LLM**.
  - `BriefingModels.swift`: `MorningBriefing` (Codable/Sendable/Equatable) + `BriefingEvent` / `BriefingTask` / `BriefingDailyLog` / `BriefingOpenLoop` / `SourceFreshnessSnapshot`. All flat snapshots — **no SwiftData model references** — so the whole briefing JSON-serializes. Real vs agent events are separate arrays (`realEvents`/`agentEvents`, each also carrying `isAgentOwned`). `SourceFreshnessSnapshot.isAbsent` is the explicit "degrade visibly" marker (`.unavailable`/`.permissionWithheld`); `MorningBriefing.absentSources` surfaces them — a missing Gmail/HealthKit is present-and-marked, never dropped.
  - `BriefingAssembler.swift`: pure assembly. Takes `now`, an injected `Calendar` (tests pass UTC for deterministic day-windowing), today's `[CalendarEventDTO]`, three `SourceFreshness` values (calendar/gmail/health), and per-goal `BriefingGoalInput` bundles. Splits/attributes events, computes due-today (window overlaps `[startOfDay, startOfDay+1d)`), delegates slip detection to Phase 3A's `SlipDetector`, and picks `topPriority` (highest-priority due task, else most-urgent slip) for the headline/widget. `BriefingGoalInput(goal:)` derives the `SlipRule` from the goal's playbook via `PlaybookLibrary`.
  - `EveningCapture.swift` + `TaskActioner.swift`: capture writes through the append-only `MemoryStore`. `TaskActioner.complete` flips `GoalTask.isComplete` **and** logs a `GoalProgress` evidence entry (metricKey from the playbook's `progressSignals`); `.skip` logs a zero-value progress note without completing. `EveningCapture.apply(CaptureInput)` batches completions/skips (via `TaskActioner`) + standalone progress marks + new `OpenLoop`s + a `DailyLog` note. The DailyLog uses a stable per-day `factKey` (`daily_log:YYYY-MM-DD`) so a second capture the same day **corrects** (revision n+1) rather than duplicating.
  - `WeeklyReview.swift`: `WeeklyReview` (Codable) + `WeeklyReviewAssembler`. Per active goal, buckets tasks into completed / slipped / next-week over a ±7-day window; carries `degradedSources` snapshots (PRD: review runs even with degraded sources, explicitly noted).

## Phase 3C — HealthKit Pacing ✅ (implemented; TDD, fixture-verified; live-capable device reader)

Additive, isolated HealthKit read → pacing suggestions on goal plans, done exactly as Phase 3A's handoff prescribed: a **pure data transform on playbook `TaskRule` values** + a visible marker at the `PlannedTask`/preview layer. No engine rewrite, no new hard dependency — nothing else in the plan requires HealthKit.

- **Contract moved to `Core`** (`Sources/Core/HealthKit.swift`): `HealthSummary` (summarized sleep/RHR/HRV — never raw samples, a local-only privacy class) and the `HealthKitDataSource` protocol now live in `Core`. Reason: the pure pacing engine lives in `Goals`, and **`Goals` must not depend on `Integrations`** (that's what keeps "no calendar writes" a *structural* guarantee — gotcha carried from 3A). Putting the pure contract in `Core` lets both the real reader (`Integrations`) and the pacing engine (`Goals`) share it without `Goals` ever importing `Integrations`. `requestAuthorization()` added with a default no-op extension. `FakeHealthKitData` re-pointed to `Core`; existing `IntegrationsTests`/`AppSmokeTests` unaffected (both already `import Core`).
- **Real device reader** (`Sources/Integrations/HealthKitDataSource.swift` → `HealthKitClient`): read-only by construction (`requestAuthorization(toShare: [], read: …)` — empty share set makes writes structurally impossible). Reads **sleep duration** (`.sleepAnalysis`, summing the granular `asleep*` values), **resting heart rate**, and **HRV (SDNN)**, summarized per day. Guarded with `#if canImport(HealthKit)` + an `#else` `.unavailable` stub so the type always exists for composition and the host build stays green. Denial/absence → empty reads, never a throw to the caller's flow (mirrors real HealthKit privacy behavior).
- **Pacing engine** (`Sources/Goals/Pacing.swift`, pure & deterministic):
  - `PacingSignal.derive(from:)` classifies recovery deterministically — sleep is primary (`< 6.5h` → poor), corroborated by RHR (`> 58`) and HRV (`< 55`); `≥ 7.5h` with no adverse signal → good; missing fields ignored, not guessed.
  - **Transform rules**: only **poor** recovery adjusts load (guidance *eases*, never *adds* — bias to caution, "pacing not medical advice"). For each adjustable rule: `expectedDuration *= 0.8` and `weeklyFrequency -= 1`.
  - **Bounds are playbook-defined** (`PacingPolicy` on `GoalPlaybook`, optional): `adjustableRuleKeys` (which rules may flex), `minDurationScale` (duration floor — never below 60%), `maxFrequencyReduction` (≤1 session dropped), plus poor-recovery targets. Frequency is floored at **1** (never zeroes a session out). Training pacing covers only the *soft* sessions (`run`, `strength`) — the immovable `fixed`/`.block` swim/ride/brick anchors are never touched. **Job Search declares no policy → never HealthKit-paced** (sleep quality shouldn't reshape an application funnel).
  - `PacedPlanner` = `GoalPlanner` + transform: adjusts the playbook, plans from it, and stamps `PacingInfluence` on affected `PlannedTask`s. With `influenceEnabled: false` it is *exactly* `GoalPlanner.generatePlan` — no markers, identical task data.
  - `HealthPacingCoordinator` (async) bridges the `HealthKitDataSource` read to the pure planner. **Denial-safe**: a throwing read is swallowed to `[]` (`try?`), so planning + the daily loop keep working with influence simply absent. Honors the toggle without ever touching goal data. `currentInfluence(...)` returns a compact `PacingInfluenceSummary` for the UI banner.
- **Visible marker**: `PacingInfluence` (Equatable/Sendable) carries `label = "HealthKit-influenced"`, `isHealthKitInfluenced == true`, a plain-language rationale, and the applied scale/frequency delta. ## Phase 4A — Proposal System & Ops Inbox ✅ (implemented; TDD, mock-verified)

- **Structural enforcement — execution ONLY via approval** (`ProposalEngine.swift`): the whole safety model rests on `ApprovalGrant`, a value whose initializer is **`fileprivate` to `ProposalEngine.swift`** and is constructed in exactly one place — inside `approve(...)`, during the `pending → approved` transition. Every `ProposalHandler.execute` **requires** an `ApprovalGrant` parameter. Consequence, checked by the compiler: no view, test, tool, or future Phase-5 code can mint a grant, so **no handler is callable except through an approved pending Proposal**. There is no back door — the engine holds the handlers privately and `approve()` is the only method that runs one. This is what makes AGENT_DESIGN's "a confused model's worst case is a pending Proposal" a *structural* guarantee, not a hope.
- **State machine** (`ProposalStatus`: `pending → approved | dismissed | snoozed | expired`; the PRD's "rejected" maps to `dismissed`, "superseded" is the orthogonal `MemoryEntity` revision chain — kept separate, as the Phase-1 model comment already documented): every transition guards `status == .pending` (else `ProposalError.notPending`). `approve()` runs the handler **first** and only marks `approved` on success — a failed calendar write leaves the proposal `pending` to retry (PRD: "not silently gone"). **Expiration DROPS, never executes**: `expirePendingPastDue()` sweeps pending-past-`expiresAt` to `expired`; `approve()` on a stale-but-still-pending proposal expires + refuses it (`ProposalError.expired`) rather than running it. Rationale is plain-language and names both blocks + the severity ("X is a fixed anchor, so Y is the one to move"; for hard fixed/fixed, "both are fixed anchors — review manually, lower-priority offered as the move candidate"). `source = .inference`, `affectedAppID = yielding task`, `factKey = proposal:conflict:<pairKey>` so re-detecting the same pair **dedupes via `enqueueBatch`'s active-factKey guard** (no stacking). Approving reschedules; dismissing leaves the plan as-is — a conflict is *surfaced*, never a silent block. `detectAndBuild(acrossGoals:now:)` is the one-call seam a scheduling flow uses right before enqueuing create-event proposals.
- **Shortcuts / iMessage intake** (`Sources/Proposals/Intake/`):
  - `PlanTextExtractor.swift` — pure, deterministic text→classification. Uses Foundation's `NSDataDetector` (seeded with an explicit reference date so relative phrases resolve reproducibly) plus a small time-of-day regex. **Conservative**: only text carrying a concrete date **and** a clock time becomes an `.event(EventCandidate)` (default 1h block); everything else valid becomes a `.note`; empty→`nil`. LLM-free. **Phase 6 can reuse this on a confirmed voice transcript** (it's dependency-free beyond Foundation).
  - `ShortcutIntakeService.swift` (`@MainActor`) — the only entry point the App Intent reaches. Validates → classifies → enqueues **at most a pending Proposal**, tagged `MemorySource.iMessage` (explicit untrusted/best-effort provenance), confidence 0.35. `.event` → `create_agent_calendar_event` (agent calendar only); `.note` → `remember_fact`. **Drops with no Proposal** on: empty/whitespace (`.empty`), `receivedAt` older than `maxAge` = 24h (`.stale`, the PRD's "delayed payload"), or an implausible future timestamp (`.future`). Re-forwarding the same text reuses a stable FNV-1a `factKey` and **collapses onto the existing pending item**. Raw text is **Local-only — never logged** (the `log` sink gets metadata only: outcome + reason + char count).
- **Intake architecture choice — App Intent (not URL scheme)** (`App/iOS/Intents/IngestMessageIntent.swift` + `PersonalOpsShortcuts: AppShortcutsProvider`): chosen because an App Intent takes a **typed `String` parameter** natively (the automation maps the message's *Content* directly — no URL-encoding of untrusted text), runs **in the background** (`openAppWhenRun = false`, so a forwarded text quietly becomes a pending Proposal), and returns a Shortcuts-surfaced dialog. A `personalops://` URL scheme was the alternative but forces the app open, needs fragile percent-escaping of arbitrary text, and is clumsier in the editor — documented as a possible future fallback (same `ShortcutIntakeService` would back it). The intent builds its own `ModelContainer` via `DataStore.makeContainer()` (shared on-disk store), constructs a `ProposalEngine` + `ShortcutIntakeService`, and enqueues. **No pbxproj change needed** — file-system-synchronized groups pick up `App/iOS/Intents/`, and App Intents are auto-discovered by the build-time AppIntents metadata processor (no Info.plist registration). Verified by the clean `xcodebuild` build.

- **Gotchas**: (1) Conflict severity is driven by `ConflictPolicy`, **not** `TaskFlexibility` — flexibility only informs which block *yields*. The fixture pairs are named by flexibility because the playbooks correlate them (training `fixed`↔`.block`, job-search `movable`↔`.warn` / `optional`↔`.allow`); don't assume flexibility grades severity. (2) `ScheduledBlock.end` uses `expectedDuration`, **not** `latestAcceptable` (the latter includes slip slack, which isn't occupied time). (3) `ShortcutIntakeService` is `@MainActor` (drives `ProposalEngine`/`ModelContext`) — construct on the context's actor; the App Intent's `perform()` is `@MainActor`. (4) The intake `factKey` FNV-1a is deliberately a **stable** hash (Swift's built-in `Hasher` is per-process randomized and would break cross-launch dedupe). (5) A `.note`-classified intake persists a `Preference` via `remember_fact` on approval — same shared handler as everything else; don't overload it for other entity types.
